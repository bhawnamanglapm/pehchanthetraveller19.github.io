## Why it matters

Pages read admin content through the trip app's own server, cached, so the single EC2 server isn't hit for every
visitor and a publish shows up at once.

## Routes

| Route | Returns | Cache |
|---|---|---|
| `GET /api/trip/destinations` | Published destinations with their facts, sources and `checkedOn` | Tagged per destination |
| `GET /api/trip/destination/<slug>` | One destination's full pack: visa, climate, festivals, permits, emergency numbers, cost range, tourism-board contact | Tagged per destination |
| `GET /api/trip/stays?destination=<slug>` | Published stays, grouped by area, creator-open first | Tagged `stays:<slug>` |
| `GET /api/trip/steps?stage=1&destination=<slug>` | Shown `step-guide` and `step-link` entries, with destination-specific links merged in | Tagged `steps` |
| `GET /api/trip/settings` | trip-page-settings, templates | Tagged `settings` |
| `POST /api/revalidate` | Copied from the existing app (1.04). Checks `REVALIDATE_SECRET`, then clears the tags for the collection and destination in the webhook body | — |

Pages can call the same server functions directly instead of going over HTTP; the routes exist for the client-side
parts and for testing.

## Rules

- Server-side only, using the read token. The browser never sees a Strapi URL or token.
- Every fact goes out with its `source` and `checkedOn`; the page decides on amber (over 30 days).
- Hidden entries (`shown = no`) never leave the server.
- If Strapi fails, serve the last cache; if none, return a clear "content unavailable" error (1.05).

## Acceptance criteria

- [ ] Each route returns the documented shape, with types shared with the pages.
- [ ] A publish in Strapi clears the right tag and nothing else.
- [x] A request with a wrong secret to `/api/revalidate` is refused. Checked on the live site, 16 Nov 2026.
- [ ] Hidden steps and links never appear in a response.
