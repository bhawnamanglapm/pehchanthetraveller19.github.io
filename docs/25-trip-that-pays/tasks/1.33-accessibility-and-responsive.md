## Why it matters

Most travellers plan on a phone, and stage 2 happens on a phone abroad with a weak signal. A page that only works
on a laptop on good WiFi fails the people it's for.

## Standards

| Area | What's required |
|---|---|
| **Layout** | Phone first. Every screen works at 360px wide with no sideways scroll. Tables (Trip Balance, checkpoint, S1 pitches) become stacked cards on phones |
| **Touch** | Tap targets at least 44×44px. Stage 2 log usable one-handed: main actions within thumb reach at the bottom |
| **Colour** | Text contrast meets WCAG 2.2 AA. Status (checkpoint colour, badges, step status) is always shown with words or icons too, never colour alone |
| **Keyboard** | Every control reachable and usable by keyboard, visible focus, logical order. The stepper and trip menu work without a mouse |
| **Screen readers** | Form fields have labels; errors are announced and say how to fix them; status changes (step Done, checkpoint colour) are announced; the Trip Balance table has proper headers |
| **Motion** | Respect "reduce motion" |
| **Language** | Plain English at about a Class 8 reading level; Hindi in phase 2 (2.06) gets the same check |
| **Speed** | Each stage loads only its own data. Test on a throttled "slow 3G" profile: the Today view is usable within a few seconds and works offline after "Save offline" (1.18) |
| **Voice input** | The mic button is optional; typing always works |

## Acceptance criteria

- [ ] An automated accessibility check (for example axe) passes on every route with no serious issues.
- [ ] A keyboard-only run through 0a → checkpoint → stage 2 log → stage 3 close works.
- [ ] A screen-reader run (TalkBack on Android at minimum) completes the first visit and one guided step.
- [ ] Every screen checked at 360px; the stage 2 day log checked one-handed on a real phone.
- [ ] The slow-network test is written down with the timings.
