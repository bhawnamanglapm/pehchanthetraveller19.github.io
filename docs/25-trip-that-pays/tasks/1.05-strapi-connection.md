## Why it matters

Strapi on EC2 stays the one admin panel for both apps. The trip app needs safe, limited access to it, and needs to
know at once when admin publishes.

## What to set up

| Item | Detail |
|---|---|
| **Read token** | A Strapi API token, read-only, limited to the trip collections (1.08–1.12). Used server-side only; never sent to the browser |
| **Write token** | A separate token that can only **create** `offer-report` and `stay-suggestion` entries (and `ai-flag` in phase 3). It can't read, edit or delete anything |
| **CORS** | Not needed if all Strapi calls go through the trip app's server routes, which is the rule. Keep Strapi's CORS list unchanged |
| **Webhook** | Add a **second** Strapi webhook on publish, unpublish and update of the trip collections, pointing to `https://<trip address>/api/revalidate` with the `REVALIDATE_SECRET` header. The existing app's webhook stays as it is |
| **Client** | One `strapi.ts` module: typed fetch per collection, `draft` content never requested, every response tagged for cache revalidation by collection and destination |
| **Failure** | If Strapi is down, pages show the last cached content with its "checked on" dates; if there's no cache, a clear "content unavailable" state, never invented content |

## Shared-Strapi care

- New collections don't rename or change any collection the existing app uses.
- Trip collections are named so they're easy to tell apart in the admin panel (proposed prefix in the display name:
  "Trip ·").
- Load on the single EC2 server: every page read is cached; the trip app never calls Strapi from the browser.

## Acceptance criteria

- [ ] Tokens exist with exactly the permissions above, checked by trying a forbidden action and seeing it refused.
- [ ] Publishing a test entry updates the trip app within a minute, without a redeploy.
- [ ] With Strapi stopped, a page still renders its cached content with dates.
