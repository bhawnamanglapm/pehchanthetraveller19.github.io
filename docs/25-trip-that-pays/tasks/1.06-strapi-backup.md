## Why it matters

Strapi runs on one EC2 server with SQLite and will hold every checked fact and stay for both apps. One disk failure
without a backup loses months of checking.

## What to do

1. Find out what backs up the SQLite file today, if anything, and write it down.
2. If nothing does: a daily job on the server copies the database file (and Strapi's uploads folder, which holds the
   stays' written-OK files) somewhere off the server. Use a safe copy method so a write in progress doesn't corrupt
   the copy.
3. Keep at least 30 daily copies.
4. Email admin if a backup fails.
5. **Ask the owner before anything that costs money** (for example paid storage).
6. Restore a copy to a test machine once, and write the restore steps down.

## Acceptance criteria

- [x] Written note of what existed before: a nightly SQLite copy on the server's own disk, keeping 7 days, with no
      off-server copy.
- [x] Daily off-server backups running, with failure emails. The off-server copy runs (private, encrypted S3 bucket,
      30 days; the server can upload but can't read or delete). A failed run is logged on the server and emailed to
      the site inbox; a forced failure on 16 Nov 2026 sent the email, and the owner confirmed it arrived.
- [x] One successful test restore, with the steps written in the admin runbook (1.38). Done 16 Nov 2026 on a laptop:
      the copy passed the integrity check, matched the published content and started Strapi. The runbook steps are
      in the CMS repo's admin runbook, §8.
