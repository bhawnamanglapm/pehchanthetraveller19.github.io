# Shipping this to Google Play and the App Store

Recorded 26 Sep 2026, when the founder set launching on both stores as a
requirement. This document records what each store actually accepts, what has
been built toward it, and the two things that currently block it.

---

## The short version

| | Google Play | Apple App Store |
|---|---|---|
| Accepts a packaged web app? | **Yes** — Trusted Web Activity | **No** — a wrapped website is rejected |
| Mechanism | TWA via Bubblewrap or PWABuilder | Capacitor shell + genuine native capability |
| Cost | $25, one time | $99 per year |
| Build machine | Any | macOS (or a cloud Mac in CI) |
| Blocked on | **A custom domain** | **The app doing something** |

## 1. Google Play — achievable, but needs the domain first

A Trusted Web Activity is a thin Android wrapper that renders the PWA
full-screen with no browser chrome. Google supports this route explicitly.

It requires **Digital Asset Links**: a file at
`https://<domain>/.well-known/assetlinks.json` proving that the app and the
site share an owner. That file must sit at the **root of a domain the founder
controls**.

The site currently deploys to
`bhawnamanglapm.github.io/pehchanthetraveller19.github.io/` — a subpath on a
domain owned by GitHub. There is nowhere to put the file and no ownership to
assert.

> **A custom domain is therefore a hard prerequisite for Google Play**, not the
> SEO nicety it has been treated as in `docs/08`. It is now the single
> highest-leverage open item in the project.

Without asset links the wrapper still installs, but shows a browser address bar
across the top, which both looks wrong and invites rejection as a low-value web
wrapper.

## 2. Apple — a wrapped website will be rejected

App Review guideline 4.2 (Minimum Functionality) rejects apps that are
essentially a repackaged website. This is longstanding and consistently
enforced; it is the most common rejection reason for exactly this plan.

Passing it means the app must do things a browser tab cannot:

- Push notifications (trip updates, departure reminders, enquiry replies)
- Genuine offline use — saved itineraries and documents available with no signal
- Device capability: camera, location, contacts, calendar, share sheet
- An account with state that persists and syncs
- Something worth opening twice

**Capacitor** is the right tool: it wraps this same web build in a native shell
while exposing native plugins, so one codebase serves web, Android and iOS. But
Capacitor is the packaging, not the argument — the native capability is the
argument.

### One piece of good news on Apple's commission

Apple's in-app-purchase requirement (3.1.1) covers digital goods. Travel is a
**real-world service consumed outside the app**, which is why Uber, Airbnb and
the booking platforms take payment directly. Booking a trip is therefore exempt
from the 15–30% commission.

Selling a downloadable itinerary or a subscription inside the app would not be.
Design the commerce around real-world services and Apple takes nothing.

## 3. What has been built (26 Sep 2026)

The PWA layer, generated by the build rather than hand-maintained:

- `manifest.webmanifest` — standalone display, scope and `start_url` derived
  from `basePath`, theme colours, app shortcuts
- `sw.js` — network-first for pages, stale-while-revalidate for assets,
  versioned caches, cross-origin requests untouched
- `offline.html` — a self-contained fallback with no external dependencies
- `assets/icons/` — 192/512 standard and maskable, plus an apple-touch-icon,
  rasterised by `src/lib/icon.mjs` and `src/lib/png.mjs` (the build has no image
  tooling, so the mark from `assets/favicon.svg` is drawn in code)
- Registration in `assets/js/site.js`, guarded so nothing breaks without it
- Head tags: manifest, apple-touch-icon, app-capable meta

The site is now installable from a browser on both platforms. That is the
foundation both store routes build on, and it is useful on its own — "Add to
Home Screen" works today.

**The generated icons are placeholders.** They are clean and on-brand, but the
stores display this asset large and it is the first impression. Replace them
with a designed icon before submitting.

## 4. The real blocker is not technical

Both stores, in different words, ask the same question: *what does someone do
when they open this?*

Today the answer is "read a brochure of 26 places with no content written yet."
Apple will reject that outright under 4.2, and Play will accept it to no
purpose, because nobody installs a brochure.

An app needs a reason to be opened twice. Candidates, all consistent with the
strategy so far: saved and shared trips; offline itineraries and documents;
enquiry and booking status; notifications; the agent portal from `docs/08` as
a separate app for suppliers.

**None of those work without a backend** — which is now the fourth separate
reason the project needs one, after enquiry forms, payments and AI.

## 5. Sequence

1. **Custom domain.** Unblocks Play, fixes SEO, and makes the brand credible to
   suppliers. Cheap, fast, and blocking three other things.
2. **Verify the PWA** on real devices — installability, offline, Lighthouse.
3. **Decide what the app does**, and build the backend that makes it true.
4. **Play via TWA.** Reachable soon after the domain.
5. **iOS via Capacitor**, once there is native capability worth reviewing.

Shipping 4 before 3 is possible and pointless. Shipping 5 before 3 will be
rejected.
